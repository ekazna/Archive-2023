# Информационно-справочная система архива организации 
> 🚧 Проект находится в активной доработке — 09.2026
## 📌 О проекте
Переработанная курсовая работа по Java (2 курс, весна 2023)

**Legacy-версия до рефакторинга:** [Archive-2023 / legacy](https://github.com/ekazna/archive-legacy)  

Это - backend-сервис для учёта документов внутреннего архива организации

### 🚀 Возможности

- регистрация, редактирование, поиск и фильтрация документов;
- разграничение доступа к документам по уровню доступа сотрудника;
- запрос копии или оригинала документа;
- выдача и возврат оригиналов с контролем их физического наличия в архиве;
- история завершённых запросов;
- списание документов без физического удаления данных;
- журнал действий пользователей;
- пагинация и фильтрация списков;
- отдельные права для `USER` и `ADMIN`.

## 🔄 Что изменилось относительно legacy-версии

Проект был существенно переработан по сравнению с исходной учебной версией:

- Серверный интерфейс на **Thymeleaf заменён на REST API**. В legacy-версии Spring MVC-контроллеры формировали HTML-страницы на сервере через Thymeleaf. Теперь backend предоставляет отдельный REST API, использует DTO для обмена данными и не зависит от конкретного frontend. Новый клиентский интерфейс планируется реализовать отдельно на React.
- **Перестроена структура приложения.** Вместо общей структуры controllers / services / repositories / models код организован _по функциональным модулям_ (document, documentrequest, audit, security и др.), а бизнес-правила и транзакции сосредоточены в service layer.
- **Убрана зависимость бизнес-логики от числовых идентификаторов.** Например, раньше права администратора определялись через ID департамента сотрудника, а действия в журнале — через числовые коды. Теперь для этого используются Role, DocumentActionType и отдельная security-модель.
- **Переработана модель запросов на документы.** В legacy-коде тип запроса и его состояние кодировались числовыми значениями в одной модели Order. Теперь используются отдельные DocumentRequest, RequestType и RequestStatus, а допустимые переходы между состояниями явно контролируются бизнес-логикой.
- **Удаление документов заменено на soft disposal.** Списанные документы и завершённые запросы сохраняются в БД, благодаря чему не теряется история операций и аудит.
- **Добавлена защита от конкурентных изменений.** Для документов и запросов используется optimistic locking через @Version; конфликт одновременных изменений обрабатывается как 409 Conflict.
- **Формализован жизненный цикл документов и запросов.** Добавлены проверки допустимых переходов состояний, контроль физического наличия оригинала, запрет дублирующих активных запросов и ограничения на списание документов, которые сейчас выданы или участвуют в активных запросах.
- **Начато автоматическое тестирование бизнес-логики.** Основные сценарии работы с запросами на копии и оригиналы покрываются unit-тестами на JUnit 5 и Mockito
- **Обновлена технологическая база проекта:** Java 17 и Spring Boot 3.0 заменены на Java 21 и Spring Boot 3.5; очищены устаревшие и неиспользуемые зависимости

### ⚙️ Дополнительные инженерные улучшения

* зависимости приложения теперь внедряются через constructor injection (вместо @Autowired);
* входные данные REST API валидируются через Bean Validation;
* обработка ошибок централизована через GlobalExceptionHandler и ProblemDetail;
*    подключение к БД и порт приложения вынесены в environment variables вместо хранения конфигурации в коде;
*    Open Session in View отключён, а преобразование entity в DTO выполняется внутри транзакционного service layer;
*    JPA-связи переведены на LAZY там, где eager loading не нужен; для необходимых связанных данных используются точечные EntityGraph;
*    из JPA entity убран Lombok @Data, чтобы избежать нежелательной генерации equals, hashCode и toString;
*    удалены ненужные bidirectional-связи, CascadeType.ALL не используется без явной необходимости;
*    фильтрация документов и запросов реализована через JPA Specification, списки поддерживают Pageable;
*    security principal отделён от JPA entity Employee; получение текущего сотрудника для бизнес-логики вынесено в CurrentUserService;
*    роль пользователя и уровень доступа к документам разделены: роль определяет доступные операции, а accessLevel — какие документы сотрудник может видеть;
*    для недоступного пользователю документа API возвращает 404, чтобы не раскрывать сам факт его существования;
*    обязательность JPA-связей синхронизирована с NOT NULL ограничениями БД;
*    удалены старые MVC-контроллеры, Thymeleaf UI, устаревшие repository queries, тестовые модели и другой legacy-код, который больше не используется.

### 🏗 Архитектура

Проект организован по функциональным модулям:

```text
com.archive.archive
├── document
├── documentrequest
├── employee
├── audit
├── reference
├── security
├── exception
└── config
```

REST-контроллеры работают с DTO и не возвращают JPA entity напрямую.  
Бизнес-логика находится в транзакционном service layer. Для выборок используются `Specification`, `Pageable` и точечные `EntityGraph`. `Open Session in View` отключён.

Ошибки API централизованно преобразуются в `ProblemDetail` с корректными HTTP-статусами.


### 🌐 REST API

Основные группы endpoint'ов:

```text
/api/v1/documents
/api/v1/document-requests
/api/v1/audit
/api/v1/reference
/api/v1/employees
```

Поддерживаются:

- получение списка и одного документа;
- создание, изменение и списание документа;
- создание запросов на копию и оригинал;
- завершение запроса копии;
- выдача и возврат оригинала;
- просмотр аудита;
- получение справочных данных.

### 🔐 Security

Аутентификация сейчас построена на Spring Security с session/cookie-механизмом.

- роли `USER` и `ADMIN` хранятся явно;
- роль определяет доступные операции;
- уровень доступа сотрудника определяет видимость документов;
- JPA entity `Employee` отделена от security principal;
- текущий сотрудник для бизнес-логики получается через отдельный `CurrentUserService`;
- CSRF-защита остаётся включённой.


### 📋 Основные бизнес-правила

#### Документы

Документ имеет статус:

- `ACTIVE` — участвует в работе архива;
- `DISPOSED` — списан и исключён из активного оборота.

Сотрудник видит только документы, уровень доступа которых не превышает его собственный.

Оригинал документа отдельно имеет признак физического наличия в архиве (`present`).

#### Запросы

Типы запросов:

- `COPY`;
- `ORIGINAL`.

Статусы:

- `REQUESTED`;
- `ISSUED`;
- `COMPLETED`.

Допустимые переходы:

```text
COPY:
REQUESTED -> COMPLETED

ORIGINAL:
REQUESTED -> ISSUED -> COMPLETED
```

Для одного сотрудника нельзя создать второй активный запрос того же типа на тот же документ.  
Документ нельзя списать, пока его оригинал выдан или по нему существуют активные запросы.

### 🧪 Тестирование

Для бизнес-логики используются JUnit 5 и Mockito.

На текущем этапе unit-тестами покрываются основные сценарии работы с запросами:

- создание запросов на копию и оригинал;
- защита от дублирующих активных запросов;
- завершение запросов на копию;
- выдача и возврат оригиналов;
- недопустимые переходы между состояниями;
- изменение физического статуса документа;
- запись событий в журнал аудита.

Тесты построены изолированно от Spring Context и БД: зависимости сервисов заменяются mock-объектами.
